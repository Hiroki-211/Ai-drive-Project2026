# TODOアプリ 要件定義書 (v1)

## 1. 目的と対象範囲

### 1.1 目的
本ドキュメントは、既存のExpress + TypeScript + EJSで構築されたWebアプリケーションに対し、TODO管理機能を追加するための要件を定義する。

### 1.2 対象範囲
- 本機能の対象は、画面 `/todo` およびREST API `/api/v1/todos` とする。
- 既存のルート `/` および `/api/db-check` は変更せずそのまま維持する。
- 画面 `/todo` からJavaScriptの Fetch API を用いて `/api/v1/todos` を非同期で操作する。
- データベースは学生各自の Neon PostgreSQL を使用し、既存の `DATABASE_URL` および接続設定を再利用する。
- デプロイ先は Vercel とする。
- 確定していない実際のファイル配置（ディレクトリ構造やサーバーサイド・クライアントサイドの具体的なファイルパス等）は「要確認」とし、設計書にて確定させる。

### 1.3 対象外事項 (V1)
- ユーザー認証および認可機能
- TODOの優先度設定
- 表示一覧の絞り込み・フィルタリング機能
- 登録済みTODOのタイトル更新機能（V1では完了状態の切り替えのみを対象とする）

## 2. 4機能と受け入れ条件

### 2.1 REQ-01: 一覧表示機能
- **操作**: 画面 `/todo` 表示時または更新処理実行後に、登録済みのTODO一覧を取得・表示する。
- **入力**: リクエストパラメータなし（`GET /api/v1/todos`）。
- **結果**: 成功時（HTTP 200）、`{"status":"success","data":[...]}` の形式でTODOオブジェクトの配列を取得し画面に表示する。データが0件の場合は `{"status":"success","data":[]}` を返す。
- **エラー**: DB接続エラーやサーバー内部エラーが発生した場合、HTTP 500または503のエラーレスポンスを返却する。
- **受け入れ条件**: 画面読み込み時にFetchで一覧が正しく取得され、描画されること。データが0件の際もエラーとならず空配列が表示されること。
- **確認方法**: 画面表示時およびデータが存在しない状態で `/todo` にアクセスし、レスポンスデータと画面表示を確認する。

### 2.2 REQ-02: 新規登録機能
- **操作**: ユーザーが入力フォームにタイトルを入力し、登録ボタンを押下してTODOを新規追加する。
- **入力**: リクエスト本文（`POST /api/v1/todos`）に `{"title": "..."}` を含める。前後の空白を除去した後の `title` は1〜100文字とする。
- **結果**: 成功時（HTTP 200または201）、DBに保存され `{"status":"success","data":{ "id": ..., "title": "...", "isCompleted": false, "createdAt": "..." }}` を返す。
- **エラー**:
  - `title` 属性の欠落、型不正の場合：HTTP 400（BAD_REQUEST）
  - 空白除去後の `title` が0文字または101文字以上の場合：HTTP 422（VALIDATION_ERROR）
  - DB接続不可・実行エラー：HTTP 500または503
- **受け入れ条件**: 有効な文字数のタイトルを入力して送信した際、新規TODOが追加され一覧に即座に反映されること。不正な文字数の場合は適切なエラーメッセージが表示されること。
- **確認方法**: 1文字、100文字、空文字、101文字以上の入力をそれぞれ送信し、成功およびエラー応答と画面挙動を確認する。

### 2.3 REQ-03: 完了状態の部分更新機能
- **操作**: ユーザーがチェックボックス等を操作し、TODOの完了/未完了状態を変更する。
- **入力**: パスパラメータにID（1以上の整数）、リクエスト本文（`PATCH /api/v1/todos/:id`）に `{"isCompleted": boolean}` を含める。
- **結果**: 成功時（HTTP 200）、対象TODOのステータスが更新され `{"status":"success","data":{ "id": ..., "title": "...", "isCompleted": ..., "createdAt": "..." }}` を返す。
- **エラー**:
  - 本文が空、IDが1以上の整数でない、または型不正の場合：HTTP 400（BAD_REQUEST）
  - 指定されたIDのTODOが存在しない場合：HTTP 404（NOT_FOUND）
  - DB接続不可・実行エラー：HTTP 500または503
- **受け入れ条件**: 完了状態の切り替え操作が行われた際、対象の `isCompleted` が正しく更新され画面に反映されること。存在しないIDや不正なIDに対する操作で適切にエラーが返ること。
- **確認方法**: 存在するIDに対するステータス変更、存在しないIDに対する送信を行い、レスポンスと画面表示を確認する。

### 2.4 REQ-04: 削除機能
- **操作**: ユーザーが削除ボタンを押下し、不要なTODOを削除する。
- **入力**: パスパラメータにID（1以上の整数）（`DELETE /api/v1/todos/:id`）。
- **結果**: 成功時（HTTP 204）、本文なしでレスポンスを返却し、画面上から対象TODOを削除する。
- **エラー**:
  - IDが1以上の整数でない場合：HTTP 400（BAD_REQUEST）
  - 指定されたIDのTODOが存在しない場合：HTTP 404（NOT_FOUND）
  - DB接続不可・実行エラー：HTTP 500または503
- **受け入れ条件**: 削除操作により対象のTODOが削除され、204レスポンスとともに一覧から消去されること。
- **確認方法**: 存在するTODOの削除を実行して204と画面変化を確認し、存在しないIDへの削除実行で404エラーを確認する。

## 3. 共通のデータ・エラー条件

### 3.1 データベース構造（`todo_tasks` テーブル）
- **テーブル名**: `todo_tasks`
- **カラム構成**:
  - `id`: INTEGER（自動採番、主キー）
  - `title`: TEXT（必須、前後の空白除去後1〜100文字）
  - `is_completed`: BOOLEAN（必須、デフォルト値 `false`）
  - `created_at`: TIMESTAMPTZ（必須、デフォルト値 `NOW()`）

### 3.2 JSON表現と変換ルール
- アプリケーション・API間で扱うTODOオブジェクト表現:
  ```json
  {
    "id": 1,
    "title": "タスク名",
    "isCompleted": false,
    "createdAt": "2026-10-28T06:00:00.000Z"
  }
  ```
- スネークケース（DB）とキャメルケース（API）の変換:
  - `is_completed` $\rightarrow$ `isCompleted`
  - `created_at` $\rightarrow$ `createdAt`（ISO 8601形式などの日時文字列に変換）

### 3.3 成功レスポンス標準フォーマット
- `GET`, `POST`, `PATCH` 成功時（HTTP 200 / 201）:
  ```json
  {
    "status": "success",
    "data": { ... } // または [ ... ]
  }
  ```
- `DELETE` 成功時（HTTP 204）: 本文なし（No Content）。

### 3.4 エラーレスポンス標準フォーマットおよび条件
エラー発生時はレスポンス本文を以下のフォーマットで統一し、セキュリティ対策としてSQL文、DB接続文字列、サーバー内部の詳細情報は含めずログ出力にとどめる。

```json
{
  "status": "error",
  "code": "ERROR_CODE",
  "message": "エラーメッセージ",
  "details": []
}
```

- **HTTP 400 BAD_REQUEST (`code: "BAD_REQUEST"`)**:
  JSONの構文エラー、必須項目の欠落、型違い、1以上の整数ではないID、PATCHの空本文。
- **HTTP 422 VALIDATION_ERROR (`code: "VALIDATION_ERROR"`)**:
  前後の空白除去後の `title` が0文字または101文字以上。
- **HTTP 404 NOT_FOUND (`code: "NOT_FOUND"`)**:
  形式が正しいIDに対応するTODOデータがDB上に存在しない。
- **HTTP 500 INTERNAL_ERROR (`code: "INTERNAL_ERROR"`)**:
  サーバー内部処理中の予期せぬエラーおよびSQL実行エラー。
- **HTTP 503 DB_UNAVAILABLE (`code: "DB_UNAVAILABLE"`)**:
  DBサーバーへ接続できない場合。

## 4. 環境別確認事項

### 4.1 動作確認およびデータ規定
- **データ運用**: 個人情報は一切扱わず、テストおよび確認には架空のデータのみを使用する。
- **DB参照範囲**: Preview環境（Vercel Preview）および Production環境（Vercel Production）の両方で同一の Neon PostgreSQL データベースを参照して動作確認を行う。

### 4.2 確認プロセス
- 開発時およびデプロイ時に、PreviewおよびProductionの双方から `/todo` 画面にアクセスし、4基本操作（一覧・登録・部分更新・削除）が共通のNeon DBに対して問題なく動作することを確認する。
- 各エラー条件（400, 422, 404, 500, 503）が発生する操作を行い、期待される標準エラーJSON構造が返却され、機密情報がクライアントへ露出していないことを確認する。
- 確定していない実際のファイル配置（`TodoApi` クラスの定義場所やルーティング設定のファイル構造等）については「要確認」とし、以降の設計書作成フェーズにて具体的に決定する。
